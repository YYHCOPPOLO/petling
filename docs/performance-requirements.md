# 轻量化与性能要求

更新日期：2026-10-21。本文是 [产品需求](product-requirements.md) 的全局约束，适用于 R01–R09 全部能力及 M0–M4 各阶段。轻量化、运行时低占用和高性能属于必须实现的目标；不能通过删除已确认功能、破坏任务恢复或丢失提醒达到指标。

当前仅完成需求与验收设计，尚未采集运行性能基线。资源清理后的 98.1 MiB 是美术资源体积，不是应用安装体积或运行内存；既有功能测试也不证明性能达标。

## 全局要求

| 编号 | 要求 | 验收关注点 |
| --- | --- | --- |
| N01 | 启动与分发轻量化 | 先显示可交互宠物，工作技能和资源按需加载；分别记录安装包、安装后体积、依赖增量和启动耗时 |
| N02 | 低占用陪伴 | 可见待机、隐藏、锁屏和静态画面分别控制渲染与轮询；闲置时不常驻无任务的解析、自动化和外部 Agent 执行进程 |
| N03 | 交互流畅 | 点击、拖拽、输入、打开面板和取消有及时反馈；任务运行、流式输出与索引不能阻塞交互 |
| N04 | 工作负载有界 | 解析、检索、桌面观察、模型调用和外部 Agent 使用有界队列、并发和内存预算；任务量增加时排队或降速 |
| N05 | 长期运行稳定 | 会话、知识和文件按需读取；缓存、日志、临时文件有容量与清理策略；重启、反复使用和长期驻留不持续积累资源 |
| N06 | 及时释放与恢复 | 任务结束、取消、面板关闭和应用退出释放对应资源；释放执行进程后仍能从持久化记录接续任务 |
| N07 | 性能可测量、可回归 | 生产构建、固定设备和工作负载下统计完整进程组；报告初始值、峰值、稳定值、分位数和资源归属 |

## 初始工程预算

下列数值是待验证的初始工程目标，不是用户指定的精确阈值，也不是当前实测结果。M0 在固定参考设备上建立基线，并版本化记录验收预算；未达标时记录差距和优化方案，不以删除功能或静默放宽指标作为通过。

参考设备先按至少 4 个逻辑 CPU、8 GiB 内存、SSD 和 60 Hz 显示器选择，固定实际型号、操作系统、架构、分辨率、缩放和电源模式。Windows 与 macOS 分别出结果，不把不同设备的数字混成同一基线。

| 场景/指标 | 初始目标 | 测量范围 |
| --- | --- | --- |
| 进程冷启动 | 可交互时间 P95 ≤ 3 秒 | 应用进程全部退出后重新启动；不强制清空操作系统文件缓存，另标识开机首启；完成宠物显示且可响应输入为终点 |
| 可见待机内存 | 应用进程组内存 P95 ≤ 250 MiB | 默认画质、正常待机动画和已启用的轻量调度，无活动工作任务；保留正常随机互动，不通过停掉宠物伪造待机 |
| 可见待机 CPU | 应用进程组平均 ≤ 5% 的单核 CPU | 一个逻辑 CPU 满载为 100%，不能直接混用操作系统任务管理器的不同百分比口径 |
| 隐藏/锁屏空闲 CPU | 应用进程组平均 ≤ 1% 的单核 CPU | 无活动工作任务；停止不可见的持续绘制和无效高频轮询，保留提醒、必要事件和恢复能力 |
| 本地交互反馈 | P95 ≤ 100 ms | 从点击、输入、打开面板或取消操作到首次可见反馈；同时测待机和工作负载下表现 |
| 拖拽与面板绘制 | 60 Hz 参考屏下有效绘制帧率 ≥ 55 FPS | 统计持续拖拽的呈现间隔和丢帧；SWF 动作按素材帧率播放，不靠重复帧提高统计结果 |
| 常规单任务内存 | 应用进程组峰值 ≤ 512 MiB | 以本文件固定工作负载测量，包含任务 worker；外部执行器另列，同时报告机器上的完整任务总占用 |
| 工作后恢复 | 任务终止后 60 秒内回到待机预算 | 关闭工作面板并经过规定的空闲回收期；完成、失败、取消三条路径分别测量 |
| 长时间与重复使用 | 稳态内存中位数增量 ≤ 20 MiB | 8 小时驻留及 50 次固定操作循环分别测量；预热后比较初末相同待机状态，记录峰值和趋势 |
| 应用退出清理 | 正常退出后 10 秒内无遗留的任务所属进程 | 包含任务创建的 worker、harness、桥和验证浏览器；共享或用户独立启动的应用不在终止范围 |

安装包与安装后体积、GPU 占用与显存、磁盘写入量、索引吞吐和大型项目搜索延迟，需在 M0 取得基线后冻结具体预算，发布前不得缺失。当前 98.1 MiB 素材记录只用于追踪资源变化；新增必要资源应说明用途和增量。

交互反馈不等于模型已经完成回答。分别记录本地反馈、模型首个输出、工具执行和整体任务耗时；网络等待及外部模型推理延迟必须单列，不能作为本地 UI 卡顿的解释。GPU、能耗和磁盘指标按平台可获得的计数器报告，不把不可测记为零。

## 进程与指标统计口径

- 应用进程组包含主进程、全部 renderer、GPU/utility、Ruffle 所在进程、应用侧 worker、桥与辅助进程。不得只测主进程或 JavaScript 堆，也不能通过把本体工作移到子进程来隐藏开销。
- 任务创建的外部 harness、本地模型服务和被启动的目标应用分别归组；同时给出应用自身、各执行器和合计的资源消耗。已有用户应用只记录可归因的任务影响，不算作任务可关闭的进程。
- CPU 使用进程组累计 CPU 时间增量除以墙钟时间，再乘 100%；超过一个逻辑 CPU 时允许超过 100%。必须记录平均、P95 和峰值及采样间隔。
- 内存默认使用各进程驻留集之和；Windows 对应 Working Set，macOS 对应 RSS。共享页可能重复统计，因此这是统一的进程组口径，不声称等于机器独占物理内存；平台支持时另报私有内存与 GPU 内存。
- 运行结果应绑定代码版本、构建方式、配置、数据样本及校验值。暖机、首次使用和长期运行分别报告；不得依赖开发工具、强制 GC 或手工关闭应正常运行的模块取得验收数字。
- 每个后端单列启动、活动和空闲回收成本；本体预算通过也不能掩盖外部执行器失控。组合任务采用显式额度和有界并发，外部进程数量及总占用随任务变化可观察。

## 架构与实现约束

1. **按需加载与按需启动。** 常驻部分保持为宠物互动、状态/任务宿主和轻量提醒调度。解析器、索引工作、桌面操作和外部后端在使用时加载或启动；保持工具发现能力，不要求所有执行器常驻。模型后端可配置，默认不随应用启动加载本地大模型。
2. **有界并发与交互优先。** 初始采用一个重任务执行槽，轻量聊天、取消和到期提醒保持响应；之后依据设备与任务预算调整。解析、索引与本地重计算移出 UI 和主进程热路径，任务积压时施加背压。
3. **状态驱动渲染。** 可见活动、可见静态、隐藏和锁屏使用不同调度。减少静态画面的重绘、过大的透明绘制区域和闲置播放器；调整动画或轮询后仍须验证拖拽、多屏、输入法、动作时序和业务事件。
4. **观察行为只随任务运行。** 桌面截图、控件扫描和文件观察按任务范围与变化节流，无任务时不持续抓屏或扫描全盘。优先使用适合任务的现有接口，避免为简单查询启动完整自动化执行器。
5. **增量数据与有限缓存。** 分段解析与检索，按内容版本复用产物；长对话分页或虚拟化，流式文字批量刷新。使用有上限的缓存和日志，避免全量历史常驻、重复索引和每个流式片段都重写完整存档。
6. **释放执行器、保留工作记录。** 进程与定时器按应用、会话、任务归属管理，空闲回收有明确期限；复用有界 worker，防止每个工具调用都创建新进程。释放与退出先落盘检查点，正在等待输入的任务不能因清理而丢失。
7. **分发与依赖控制。** 沿用资源依赖审计和去重打包；新增依赖报告安装与运行成本。默认安装不捆绑未使用的模型、多个后端完整运行时或额外浏览器；需要额外运行环境的技能清楚展示就绪状态和获取方式。

隐藏或锁屏时降频只影响展示和无效观察，不暂停用户要求继续的任务、提醒或任务状态落盘。省电不能以丢通知、丢业务效果、弱化隔离或停止结果核验为代价。

缓存淘汰只释放可重建的数据，不删除用户笔记、长期记忆、任务产物或恢复检查点。日志与临时文件清理需区分调试记录、执行事实和用户数据，保持工作交接所需记录可用。

## 当前代码的待测位置

以下是静态代码审阅发现的测量入口，尚不能据此断言具体瓶颈：

| 位置 | 当前行为 | 测量与优化方向 |
| --- | --- | --- |
| `src/main/window.ts` | 透明窗口覆盖当前显示器工作区，光标每 33 ms 采样 | 分辨率/DPI 对 GPU、内存和重绘的影响；拖拽与空闲分别调度，验证多屏和悬停不回退 |
| `src/renderer/pet/machine.ts` | 启动后按 12 Hz 检查动作状态 | 静态动作、隐藏和锁屏期间的无效唤醒；增加可释放的生命周期，不破坏动作完成事件 |
| `src/renderer/swf/pet-swf.ts` | 双播放器交替加载动作以避免闪烁 | 统计 WASM、纹理和闲置播放器成本；评估有限预加载与回收，保留无闪烁切换 |
| `src/renderer/pet/store.ts`、`src/main/save-repository.ts` | 200 ms 合并提交，主进程同步序列化并写 JSON | 持续拖拽、重复命令时的主线程耗时和磁盘写入；优化增量与批次时保持提交顺序、退出保存和请求去重 |
| `src/core/pet/result.ts` | 通过分组 JSON 序列化比较生成 patch | 在大存档与连续命令下测 CPU、分配和 GC；按测量结果替换比较方式 |

先在现有 Electron + Ruffle 上建立基线并定位开销。如仍无法满足冻结预算，再单独验证窗口、渲染器或桌面外壳的替代方案；比较内存、CPU、包体、兼容性和迁移成本。框架名称本身不构成性能达标依据。

## 性能验收流程

1. 使用 Windows/macOS 的生产构建和隔离测试数据，记录设备、系统、运行配置、缩放、电源模式、版本及后台负载；不操作用户真实存档。
2. 测量至少 10 次进程冷启动和首次打开技能面板，启动样本单独报告；记录首次加载开销，避免只报告预热后结果。
3. 每种待机状态预热 2 分钟、采样至少 10 分钟，以 1 秒间隔采集进程组 CPU、内存、进程数及可用的 GPU/磁盘指标。显示、隐藏、锁屏和唤醒分别测量。
4. 建立固定工作负载：1,000 条会话消息、1,000 条笔记/待办、100 个提醒；10,000 个文本文件且总计约 100 MiB 的项目；100 页、约 10 MiB 的文本 PDF。样本内容、大小和校验值固化，大文件和超限输入另设边界场景。
5. 对这些样本串行运行查询、阅读和整理，同时操作宠物；再测队列积压、一个参考外部后端和受支持桌面流程。固定模型事件可用于复现本地性能，真实后端成本必须另测并注明，不能拿模拟结果证明完整协作性能。
6. 交互场景收集至少 100 次输入反馈延迟，拖拽连续测量至少 30 秒并报告帧间隔。完整流程重复至少 3 轮，均保留原始结果；待机预算在默认陪伴设置下验收，关闭主动模型请求的测量只作分项诊断。
7. 对面板开关、动作切换、任务完成/失败/取消运行 50 次固定循环，再做 8 小时驻留；比较预热后与结束后同状态的 10 分钟内存中位数，观察资源是否持续增长。
8. 检查应用退出、测试结束时的进程树与临时资源。只清理本次启动的对象，保留用户独立浏览器、终端、Agent 和应用。

报告应包含原始采样、汇总、场景、预算对照、失败原因、优化前后差异及清理结果。所有新增技能必须同时通过功能和对应性能验收；每个里程碑做快速性能回归，发布前执行完整长期测试。硬预算超限或同场景指标较冻结基线退化超过 10% 时，应复测确认并记录处理结果，不能只凭总平均值放行。

M0 负责建立基线、采样工具和预算；M1 验证核心常驻成本；M2 验证全部本体技能和执行期间响应；M3 验证多后端/应用组合；M4 完成跨平台、长期驻留、分发体积与进程清理验收。实际结果归档到 [验证记录](verification.md)，未执行的场景继续标为未测。
